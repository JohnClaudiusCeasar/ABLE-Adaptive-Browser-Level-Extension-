# User Preferences
- Prefers MySQL over SQLite as database provider for Laravel projects. Confidence: 0.9
- Prefers the agent to perform setup tasks directly (install dependencies, configure files, run migrations) rather than just providing instructions. Confidence: 0.8
- Expects the agent to diagnose root causes and apply immediate fixes when issues are flagged, not just explain the problem. Confidence: 0.8
- Prefers entering plan mode and reviewing a detailed, phased plan before any implementation begins. Confidence: 0.9
- Likes phased implementation with progress tracking (todo lists) to see what's done and what's next. Confidence: 0.8
- Works with Laravel + React/TypeScript + Inertia.js + TailwindCSS + shadcn/ui (Radix) stack. Confidence: 0.9
- Uses Laravel Fortify for authentication scaffolding (not Breeze or Jetstream). Confidence: 0.8
- Develops on a Windows machine (Windows-style paths, e.g. D:\Projects\). Confidence: 0.9
- Favors dark-themed UIs with glass-morphism styling (translucent panels, backdrop blur, subtle borders) and green accent colors. Glass-morphism treatment extends to all UI elements including small components like status badges/pills (semi-transparent tinted backgrounds, colored text instead of white, subtle opacity borders, backdrop-blur). Confidence: 0.9
- Uses a design-first workflow: prototypes UI layouts in plain HTML/CSS in a separate "Layout-Proposal" directory before implementing in the framework stack. Confidence: 0.8
- Prefers highly specific, detailed instructions with exact placement language (e.g., "subheader on the next line, placed just close and sticking to the text"). Confidence: 0.8
- Favors icon-based vertical nav cards with status indicators over traditional horizontal list navigation in sidebars. Confidence: 0.7
- Prefers extracting reusable components (glass panels, data tables, status badges, metric cards) rather than inline styling. Confidence: 0.8
- Likes colored glow/shadow effects (e.g., green glow borders with box-shadow) as a UI design signature. Confidence: 0.8
- Uses pnpm as the JavaScript package manager (not npm or yarn). Confidence: 0.9
- Provides instructions as a numbered list of distinct tasks for batch implementation. Confidence: 0.8
- Specifies exact numeric CSS values (e.g., "py to 22") rather than approximate Tailwind classes. Confidence: 0.8
- Sometimes provides desired output as exact HTML markup/code snippets with precise class names and inline styles, expecting the agent to apply them verbatim. Confidence: 0.8
- Prefers sticky sidebar + sticky header with only page content as the scrollable area. Confidence: 0.8
- Prefers minimal sidebar branding: text-only logo, no icon/image. Sidebar footer should be completely clean — no logout button, no user profile, avatar, or secondary menu buttons. Confidence: 0.8
- Prefers the logout button in the header (top-right, right-aligned via `justify-between`) rather than in the sidebar footer. Confidence: 0.8
- Prefers brand/logo elements (e.g., "ABLE" text) to be purely decorative read-only text — no hover, active, focus, or click states. Brand should not be wrapped in a button or link. Confidence: 0.8
- Prefers non-collapsible sidebars — always fully expanded, no collapse toggle or SidebarTrigger in the header. Confidence: 0.8
- Gradient backgrounds should only be applied to layout chrome (sidebar, main background/SidebarInset), never on individual page content containers. Confidence: 0.8
- Prefers sharp/angular edges — no rounded corners on the main content area container (SidebarInset). Confidence: 0.7
- Wants gradient treatment applied consistently across all layout chrome elements (both sidebar and main background), not just one. The sidebar's gradient is the canonical source of truth — all other elements (header, SidebarInset, body) should match it. Confidence: 0.9
- Prefers strict scroll boundary isolation: sidebar scroll must never bleed into the content area, and content scroll must not affect the sidebar or header. Use overscroll-contain and proper height constraints to enforce this. Confidence: 0.8
- Prefers visual separation between sidebar and content via inner shadows (e.g., `inset -8px 0 15px -5px rgba(0,0,0,0.5)`) rather than gaps, margins, or visible borders. Sidebar and content should be flush/seamless. Confidence: 0.8
- Prefers the header to use a solid color matching the sidebar's primary green tone (`#1e4b3e`) rather than its own gradient — gradient treatment is reserved for the sidebar and main background only. Confidence: 0.8
- Prefers brand text (e.g., "ABLE") centered and prominent in the sidebar, with large font sizes (40px+) and generous letter spacing. Caption text should also be a reasonable size (12px+) rather than tiny. Version number should be positioned absolutely relative to the brand name rather than inline as a superscript. Confidence: 0.8
- Prefers section dividers styled as dash-dot-dash (e.g., `-- * --`) using horizontal rules flanking a small dot, rather than standalone glowing dots or simple horizontal lines. Confidence: 0.8
- Prefers asymmetric vertical spacing in dashboard layouts: tighter gaps (`mb-3`) between text-based metric cards, and more breathing room (`mb-5`) before chart and log sections. Confidence: 0.8
- Prefers related metrics displayed side-by-side inside a single glass card (2-column grid), while unrelated or standalone metrics get their own separate card. Confidence: 0.8
- Prefers key summary/overview metrics (e.g., data transfer totals) positioned prominently at the top of the page, just beneath the header and subtitle, before other dashboard sections. Values a clear visual hierarchy with high-level KPIs first. Confidence: 0.8
- When a design/style is approved on one page, expects it to be promoted to a shared component and used as the website-wide default (e.g., "make this pill design the default for the website"). Values cross-page visual consistency. Confidence: 0.85
- Prefers avoiding redundant navigation: if a page is already accessible from a main/sidebar icon, remove duplicate navigation entries from sub-page sidebars to keep them clean and minimal. Confidence: 0.8
- Prefers semantic Tailwind color classes (`text-muted-foreground`, `text-foreground`) over hardcoded hex color values (`text-[#b2c4cb]`, `text-[#f8f8f8]`) for maintainability and theme compatibility. Confidence: 0.85
- Expects theme-aware styling implemented with Tailwind `dark:` variants and CSS custom properties (`--background`, `--foreground`, etc.) so light/dark mode toggles work correctly across all components. Confidence: 0.85
- In light mode, prefers clean white backgrounds for layout chrome (sidebar, body, SidebarInset) — no green tint. Light mode gradients should range from pure white (#ffffff) through very light grays (#f9fafb, #f3f4f6). Dark mode retains the original deep green palette and green gradient fill. Confidence: 0.9
- Expects light/dark mode styling to cover ALL layout elements comprehensively (sidebar, header, content container/SidebarInset, glass cards) — not just one or two pieces. Every structural element must have matching theme variants. Confidence: 0.9
- Prefers Tailwind CSS classes with `dark:` variants over inline `style` attributes for most theme-aware components. However, for complex multi-stop gradients (e.g., sidebar gradient with three color stops), accepts CSS custom properties defined in `:root`/`.dark` blocks and referenced via inline `style` attributes, since Tailwind's `dark:` gradient variants can be unreliable for dynamic theme switching. Confidence: 0.85
- Uses a consistent opacity-based pattern for subtle interactive surfaces: `bg-black/5 dark:bg-white/10` for inputs, dropdowns, progress bars; `hover:bg-black/5 dark:hover:bg-white/10` for hover states on pagination and interactive elements. Confidence: 0.8
- Prefers `border-black/10 dark:border-white/10` for table row separators and subtle dividers in light mode, replacing hardcoded dark-only border colors. Confidence: 0.8
- When implementing theme support, expects the assistant to proactively audit all related pages for hardcoded dark-only colors and fix them in a single pass, rather than waiting for the user to report each remaining issue. Confidence: 0.8
- When a project has multiple directories that could be the target (e.g., Layout-Proposal vs Server-Admin), expects the assistant to confirm which directory to apply changes to before proceeding, rather than assuming. Confidence: 0.85
- Server-Admin is the canonical implementation target for features; Layout-Proposal is strictly for design prototyping/mockups. Implementing features in Layout-Proposal instead of Server-Admin is considered a mistake. Confidence: 0.9
- Prefers automatic domain visit logging on every page load (not gated behind modal consent), with session-based debouncing (e.g., 5-second window via chrome.storage.session) to prevent rapid duplicates from refreshes/navigation. The modal consent flow is for UX acknowledgment only, not for controlling telemetry. Confidence: 0.85
- Casual and forgiving when mistakes are made — uses humor ("I knew it lol") and minimizes the issue ("minor mistake") rather than expressing frustration. Prefers the assistant to simply correct course without excessive apology. Confidence: 0.7
- Prefers consolidated/unified database tables over multiple normalized tables when data is closely related (e.g., merging domain_policies and domain_visits into a single table with visit tracking columns). Values simplicity in data models over strict normalization. Confidence: 0.8
- Prefers clean-slate resets over incremental patches when accumulated changes create complexity (e.g., "drop the migrations and seeders and let's start from scratch"). Would rather delete and recreate than untangle messy intermediate states. Confidence: 0.8
- When working on Chrome extension code, expects the agent to proactively verify MV3 (Manifest V3) architecture compliance — e.g., ES module usage, service worker lifecycle, importScripts compatibility — and flag issues as part of any implementation plan. Confidence: 0.8
- Uses an "Implementation" directory (alongside the "Layout-Proposal" directory) to store feature specifications and layout markdown files. Implementation files serve as concrete specs the assistant should reference and follow during coding, distinct from the prototyping role of Layout-Proposal. Confidence: 0.8
- Prefers custom CSS styling on native HTML form elements (e.g., `<select>` option backgrounds) to maintain dark theme consistency, rather than replacing them with custom component libraries. Native elements should be kept but styled via CSS in `app.css` to match the theme. Confidence: 0.8
- Prefers detail modals to include contextual visual identifiers (e.g., fetching and displaying a domain's favicon via Google Favicon API next to the domain name) for quick visual recognition. Confidence: 0.8
- Prefers click-outside-to-close behavior on all modals — expects the backdrop to dismiss the modal when clicked, in addition to a close button. Confidence: 0.85
- Prefers displaying sanitized/anonymous identifiers (e.g., generated user IDs like `ABLE-XXXXXXXX`) in UI instead of raw numeric metrics, favoring privacy-conscious presentation of user-related data. Confidence: 0.8
- Expects native `<select>` dropdown option backgrounds to be explicitly styled for dark mode (e.g., `background-color: #1a2f2b; color: #f8fafc` under `.dark`) — the default white option background in dark mode is considered a readability bug. Confidence: 0.9
- Prefers two-phase modal UX with progressive disclosure: Phase 1 is a single dropdown for type/category selection, Phase 2 is a context-specific form that changes based on the selection. Avoids overwhelming the user with all fields at once. Confidence: 0.85
- Prefers database-backed dynamic content over hardcoded frontend data arrays — when a page uses static/hardcoded data, expects the agent to create migrations, Eloquent models, and controllers to make it fully CRUD-capable via the backend. When phrases like "server integration," "live database/migration data," or "captured from the extension" are used, expects actual database queries and new tables/models/controllers — NOT mock or placeholder data. Confidence: 0.95
- Uses 'Unbounded' as the display/heading font family (applied via inline style `fontFamily: "'Unbounded', sans-serif"` on headings and modal titles). Confidence: 0.8
- Prefers consistent offline caching patterns across all features — when one feature (e.g., domain policy) has a server→offline-cache flow, expects other features (e.g., risk patterns) to mirror the same behavior. Values architectural consistency in caching strategy. Confidence: 0.85
- Prefers offline caches to auto-clear/refresh when the server comes back online — cached data should be treated as stale fallback that gets replaced with fresh server data as soon as connectivity is restored, not persisted indefinitely. Confidence: 0.85
- Prefers phased implementation: UI/layout changes first with mock/hardcoded data, database integration deferred to a separate session. Explicitly scopes work sessions to "UI-only" when desired ("retain its hardcoded status as of now for this session"). Confidence: 0.85
- Expects strict scope adherence: only explicitly mentioned items should be modified; unmentioned elements must be left completely untouched ("leave them as it is for now"). Confidence: 0.9
